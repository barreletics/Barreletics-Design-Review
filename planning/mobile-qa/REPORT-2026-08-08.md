## Headline

**The PDP scrolls sideways on a phone.** `Barreletics PDP - Definitive-v19.html` has a
document width of **525px inside a 390px viewport** — the entire page slides 135px
horizontally. One element causes it: the `Closed Sole / Open Sole / One-Offs / Outdoor`
tab row.

The same element is broken on the Home page, where `body { overflow-x: hidden }` hides the
sideways scroll but silently makes the **"Outdoor" tab unreachable** — it renders at x=513
on a 390px screen with no way to scroll to it.

**The shipping code for this is now fixed** in `shopify-build/sections/variant-grid.liquid`.
The two mocks are locked, so they still show the bug and need your call.

## Issue 1 — `.variants-tabs` overflows the viewport · SEVERITY: HIGH

| Page | Tab row width | Viewport | Page scrollWidth | Effect |
|---|---|---|---|---|
| PDP v19 | 508.9px | 390px | **525px** | whole page scrolls sideways 135px |
| Home WORKING | 496.9px | 390px | 513px (masked) | "Outdoor" tab unreachable |

**Root cause.** At mobile, `.variants-toolbar` becomes `flex-direction: column` but keeps
`flex-wrap: wrap` from its base rule. A *wrapping column* flex container sizes its cross axis
(width) to its widest item, so the toolbar hands `.variants-tabs` as much width as the tabs
want. The `overflow-x: auto` already on `.variants-tabs` never engages, because the box was
never constrained in the first place. Parent chain measured: `.variants-toolbar` correctly
358px, `.variants-tabs` inside it 508.9px.

**Fix applied** — `shopify-build/sections/variant-grid.liquid`, inside the existing
`@media (max-width: 768px)` block only (desktop untouched):

```css
.variants-toolbar { flex-wrap: nowrap; }
.variants-tabs    { min-width: 0; max-width: 100%; }
```

Verified by injecting the same rules into throwaway copies of both mocks: page `scrollWidth`
drops **513 → 390** (Home) and **525 → 390** (PDP), overflow count goes to zero, and the tab
row becomes a proper horizontal scroller at both 390px and 360px.

**Needs your call:** `Barreletics PDP - Definitive-v19.html` and
`Barreletics Home - Definitive-WORKING.html` are locked, so I did not touch them. They will
keep showing the sideways scroll until you authorise a v20 / refreshed WORKING mock. The
Shopify side is already correct.

## Issue 2 — Home 50/50 sections never collapse and are scaled 110% · SEVERITY: HIGH

`Barreletics Home - Definitive-WORKING.html`, sections `#never-loses-grip` and `#one-pair`:

- rendered **429px wide at left = −19.5px** — bleeding 19.5px off *both* screen edges
- still **two-column** on a phone: computed `grid-template-columns: 195px 195px`
- computed `transform: matrix(1.1, 0, 0, 1.1, 0, 0)`

**Root cause** is a malformed selector list in the mock's own `@media (max-width: 768px)`
block. The comment states the intent, and the rule does the opposite:

```css
/* Stack all 50/50s cleanly — override inline min-heights */
.split-section,
.split-section[style],
.coperni-live__video { transform: scale(1.1); }
```

The `grid-template-columns: 1fr` collapse rule was lost, and `.split-section` instead
inherited the video's zoom. The arithmetic confirms it exactly: 390 × 1.1 = **429**, and
−(429 − 390) / 2 = **−19.5**. So each 50/50 renders as two ~195px columns, then gets blown
up 110% and cropped on both sides.

**This is mock-only.** `shopify-build/sections/fifty-fifty.liquid` correctly collapses to
`grid-template-columns: 1fr` at 768px and carries no stray scale. The only `scale(1.1)` in
`shopify-build/` is on `.collab-hero__video`, which is intentional. **No repo fix needed** —
the storefront behaviour is right and the mock misrepresents it.

**Needs your call:** Home WORKING is locked. Confirmed fix is one line —
`.split-section { transform: none; grid-template-columns: 1fr; }` — verified to take Home's
overflow to zero, but it requires your say-so to edit that file.

## Issue 3 — mock banner covers the site nav · SEVERITY: MEDIUM · FIXED

The review banner is `position: sticky; top: 0; z-index: 100`; the nav is sticky at a
hardcoded `top: 56px; z-index: 50`. On a phone the banner text wraps to 2–3 lines and grows
well past 56px, so it sits on top of the nav.

| Page | Banner height @390px | Result |
|---|---|---|
| FAQ v6 | 111px | nav **completely hidden** |
| Journal v5 | 76.2px | nav **completely hidden** (a later rule resets nav to `top: 0`) |
| Help v3 | 58.8px | 2.8px clip |
| Returns v3 | 58.8px | 2.8px clip |
| Size Chart v1 | 58.8px | 2.8px clip |
| Contact v1 | 41.4px | 14.6px seam gap under the banner |

**Fixed in all six** (none are locked) with one uniform, desktop-safe block appended to each
file. The banner is review chrome, so below 768px it stops sticking and the nav pins to 0 —
which is robust no matter how many lines the banner wraps to:

```css
@media (max-width: 768px) {
  .mock-banner { position: static; }
  .site-nav { top: 0; }
}
```

Re-measured after the fix: each page now reports a single sticky element (the nav) instead
of two overlapping ones.

Home, Collection v18 and SEO v36 carry no mock banner and were already correct.

**Note:** `PDP v19` has **zero** sticky elements at 390px — its nav does not stick at all on
mobile, and the sticky ATC does not appear in the mock. Worth confirming that is intentional.

## Issue 4 — tap targets under 44px · SEVERITY: MEDIUM · partly fixed

Every page reports 28–53 elements under 44px tall, but the bulk are inline footer and nav
text links that are short by design. Filtering to real controls:

| Page | Control | Height | Status |
|---|---|---|---|
| PDP v19 | "Size chart" button | **16px** | locked — your call |
| PDP v19 | size buttons S / M / L | 40px | locked — your call |
| Collection v18, SEO v36 | size buttons M / L | 28px | locked — your call |
| Collection v18, SEO v36 | category tabs (All / Closed Sole / Open Sole) | 36px | locked — your call |
| Home, Collection v18, SEO v36 | "See all colors & styles" | 24px | locked — your call |
| FAQ v6 | "Expand all" | 22px | **fixed** |
| Journal v5 | "Subscribe" | 42px | **fixed** |

**FAQ v6** — grew the hit area to 44px with a transparent overlay pseudo-element so the
control renders identically (the underline has to stay tight to the text):

```css
.faq-toolbar__toggle { position: relative; }
.faq-toolbar__toggle::after {
  content: ""; position: absolute; left: 0; right: 0;
  top: 50%; transform: translateY(-50%); height: 44px;
}
```

Note the harness still flags this one, since it measures the element box rather than the
overlay. That is expected.

**Journal v5** — this mock was simply missing the stacked-newsletter rule that
`shopify-build/assets/chrome.css` (line 568) and every sibling mock already ship, so
Subscribe sat at 42px. Restored `width: 100%; min-height: 48px` to match the design system.
Mock drift, not a design change.

I deliberately did **not** bulk-resize inline text links: that is a systemic change across
locked files and would touch the type system.

## Issue 5 — text below 12px · SEVERITY: LOW · reported only

11px is the Type OS label scale (uppercase eyebrows, trust strips) and appears on all 10
pages by design. Type OS is SETTLED, so it is untouched.

Genuine legibility risk sits at 8–9px, and **every instance is in a locked file**:

| Size | Element | Pages |
|---|---|---|
| **8px** | "Sold Out" badge | Home, Collection v18, SEO v36 |
| **8px** | "LE" badge | PDP v19 |
| 9px | `.var-card__badge` ("Closed Sole") | Home, Collection v18, Journal v5 |
| 9px | "Coming soon" (`.buy-size-range`) | PDP v19 |
| 9px | `.coperni-live__meta` | Home |

8px is below the practical floor for a phone. Both 8px cases are status badges that the
freeze registry marks as REQUIRED, so they matter commercially. Recommend lifting the badge
floor to 10px — but that is a type decision and needs you.
